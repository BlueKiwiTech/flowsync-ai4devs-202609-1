# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository context

FlowSync is a course project (LIDR AI4Devs). This repo is a **cohort repo** derived from the canonical `LIDR-academy/flowsync-ai4devs-fundacional`. Course content is delivered as branches per session: `sN/start` and `sN/end`, where `s(N+1)/start` equals `sN/end` (the previous session's solution). `COHORTES.md` and `scripts/publicar-cohorte.sh` are TA tooling for publishing those branches to cohort repos — not part of the app; don't push course branches manually.

Two independent npm projects, no root workspace: `backend/` and `frontend/`. Run commands from inside each directory.

## Commands

### Backend (`backend/`, AdonisJS 7 + Lucid + SQLite)
```bash
npm run dev            # node ace serve --hmr (port 3333 by default)
npm test               # node ace test (Japa) — all suites
node ace test unit     # one suite (suites: unit, functional)
node ace test --files tests/functional/auth.spec.ts   # single file
node ace test --tests "test title"                    # single test by title
npm run lint           # eslint
npm run typecheck      # tsc --noEmit
npm run format         # prettier
node ace migration:run # run migrations (also regenerates database/schema.ts)
node ace generate:key  # fill APP_KEY in .env
```
Copy `.env.example` to `.env` and set `APP_KEY` before first run. Tests use `.env.test` (`SESSION_DRIVER=memory`). The SQLite DB lives at `backend/tmp/db.sqlite3`.

### Frontend (`frontend/`, React 19 + Vite 8 + TypeScript)
```bash
npm run dev       # vite dev server (port 5173)
npm run build     # tsc -b && vite build
npm run lint      # oxlint
```
The frontend is still the stock Vite template; there is no API integration yet and no test runner configured.

## Backend architecture

- **Subpath imports**: code imports via `#controllers/*`, `#models/*`, `#validators/*`, `#transformers/*`, `#database/*`, etc. (defined in `package.json` `imports`). Use these instead of relative paths.
- **Generated files — do not edit by hand**:
  - `database/schema.ts` is generated from migrations by `node ace migration:run` (schema generation enabled in `config/database.ts`; custom rules in `database/schema_rules.ts`). Models extend these generated classes, e.g. `User extends compose(UserSchema, withAuthFinder(hash))` — add columns via a migration, not by declaring them on the model.
  - `.adonisjs/server/*` (e.g. `controllers.ts`) and `.adonisjs/client/*` (Tuyau route registry) are regenerated by the `indexEntities`/`generateRegistry` hooks in `adonisrc.ts` when the dev server/ace runs. Routes reference controllers through `controllers.X` from `#generated/controllers`, so new controllers appear there automatically.
- **Routing** (`start/routes.ts`): API lives under `/api/v1`. `auth/*` (signup, login) is public; `account/*` (profile, logout) uses the named `auth` middleware.
- **Auth**: default guard is `api` — opaque access tokens (`DbAccessTokensProvider` on `User.accessTokens`), sent as Bearer tokens. A session `web` guard is also configured but unused by routes. `silent_auth_middleware` runs on every routed request.
- **Responses**: `providers/api_provider.ts` adds `ctx.serialize()`, which wraps payloads in `{ data: ... }` and validates Lucid pagination metadata. Controllers shape output through transformers (`app/transformers/*`, `BaseTransformer.pick`) and return `serialize(...)`. `force_json_response_middleware` forces JSON for all requests (including errors).
- **Validation**: VineJS validators in `app/validators/` created with `vine.create(...)`, consumed via `request.validateUsing(...)`.
- **Tests**: `tests/bootstrap.ts` wires Japa with `apiClient`, `authApiClient` (`.loginAs(user)`), `sessionApiClient` and DB assertions; the `functional` suite starts the HTTP server. Test files go in `tests/unit/**/*.spec.ts` or `tests/functional/**/*.spec.ts` (none exist yet).

## Reglas de proceso
- Antes de tocar código: crear una rama nueva (`git checkout -b feat/<slug>`). Nunca
commitear directo en `main`/`s1/start`.
- Al cerrar la tarea: usar la skill `/commit`, luego `gh pr create` con una descripción
completa de los cambios en el cuerpo del PR.
- Después de abrir el PR: usar el subagente `adversarial-reviewer` sobre él, antes de
darlo por terminado.
- No repitas ese resumen en el chat: la sesión se va a perder, el PR no. Responde solo
con la URL del PR.
